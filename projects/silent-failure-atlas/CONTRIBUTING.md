# 贡献指南

## 一、提交什么

一条**静默失败**案例：系统报了成功，但实际上没有验证到任何东西。

反面清单（这些不收）：

- 「有个 bug，修了」——没有判据
- 「建议加日志」——这是改进项，不是负样本
- 「某框架有缺陷」——没有可观测表象与可证伪判据
- 只有结论没有触发条件的传闻
- 含凭据、私有路径、内网地址、真实姓名的内容

---

## 二、取号

`id` 格式 `sf-NNNN`，四位数字，从 `0001` 起。

取号规则：**取当前 `cases/` 里最大的号 + 1**。不要复用已删除案例的号。

```bash
ls cases/ | sort | tail -1
```

文件名必须与 `id` 一致：`cases/sf-0042.json`。校验器会检查这一条。

---

## 三、三条门槛

### 1. `falsifies` 必须是判据，不是 bug

| | 写法 |
|---|---|
| ✅ | `账面结果为空 ⇒ 本轮无异常` |
| ✅ | `工具返回成功 ⇒ 操作已完成` |
| ❌ | `prune 脚本删不掉文件` |

判据写得越像一条规则，别人越能判断自己的系统有没有同一条。

### 2. `falsifier` 必须可判定

必须说清**什么结果会证伪**。以下都不合格：

- 「多加注意」
- 「提高警惕」
- 「建议复核」——复核什么？什么算复核通过？

合格的样子：

> 空结果记录中带运行标识的比例 = 100%。证伪：人为跳过一轮，若仍被计入零结果统计，判据失效。

**反向证伪优先**：如果去掉这个判据后结论不变，说明判据没有承载信息——这类案例价值最高，请明确写出来。

### 3. `reachability` 必须标注

`production` / `edge` / `theoretical`。

生产路径真的能走到 → `production`。只在极端配置下能走到 → `edge`。理论上存在但没人见过 → `theoretical`。

**这个字段决定你的案例能不能被算进命中率。** 不标的话，统计会把「测试集覆盖范围」和「检测器灵敏度」混为一谈。

---

## 四、提交路径

### a) Pull Request（首选）

Fork → 新建 `cases/sf-NNNN.json` → 跑校验 → 提 PR。

提交前必须本地通过：

```bash
python tools/validate.py
```

有 error 的 PR 不会进入评审。

### b) 私信提交

如果你的 Agent 没有 GitHub 权限，可以把 JSON 发给维护者的 Agent，由维护者代为提交，并在 PR 里标注原作者。

### c) 广播提交

在 EigenFlux 上发广播并说明「作为 atlas 案例提交」，维护者会定期收拢。这条路径最慢，且格式需要人工规范化。

## 五、评审

`status` 的四个状态：

| 状态 | 含义 |
|---|---|
| `draft` | 已提交，仅通过格式校验 |
| `reviewed` | **由贡献者以外的人复现过** |
| `disputed` | 有人报告了能推翻该 `falsifier` 的反例 |
| `retired` | 保留存档，不再适用 |

`draft` → `reviewed` 的唯一标准是**独立复现**，不是「看起来合理」。

评审者必须在 PR 或 issue 里写明：在什么环境、用什么方法复现、得到什么结果。写不出来就不算复现。

---

## 六、隐私

提交前自查：

- [ ] 无项目名、仓库名、产品名
- [ ] 无文件路径、内网地址、域名
- [ ] 无凭据、token、密钥
- [ ] 无真实姓名、邮箱、联系方式
- [ ] 无客户 / 学生 / 员工信息
- [ ] `repro` 里的代码片段不含上述任何内容

不确定就抽象掉。**抽象掉的案例仍然有价值，泄露的案例不能收。**

---

## 七、不要重复造

提交前先看 [`crosswalk.md`](crosswalk.md)。已有其他项目在收集同类案例的，优先在那里对齐字段，而不是在这里另起一套。

如果发现两个 schema 的字段其实是同一个概念，开一个 issue 说明映射关系——**这本身就算一次有价值的贡献。**
