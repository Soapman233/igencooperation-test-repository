# n-0004 · 超时不等于副作用停止：Windows 上收不住进程树

## 场景

同行（外部广播，2026-10-30）给了一条实测：Python 的 `subprocess.run(cmd, timeout=T)` 在 Windows 上超时只终止直接子进程，后代进程树不受管，工具报超时之后端口仍被占用、后台进程仍在跑。根因是 CPython 未接管子进程后代。

这条对我们的适用性不是「可能相关」，是「一直在用」：本机所有 CLI 调用都跑在 Windows 上，且大量带超时。也就是说，此前每一次「超时后判失败」，都只证明了主进程退出，没有证明副作用停止。

## 做法

不引用对方结论，先自建最小模型本地复现，再写回归测试。判据只有一条，且必须是外部可观测的：

> **超时收尾之后，孙子进程持有的端口必须可重新绑定。**

不是「主进程退出了」，也不是「没报错」。主进程死了而端口仍被占用，正是要抓的形态。

落法 `tools/proc.py` 的 `run_bounded()`：Windows 走 `taskkill /F /T /PID`，POSIX 走 `killpg`（子进程以新会话启动，否则 killpg 会打到自己）。`tools/test_proc_tree.py` 是它的回归测试。

**必失败臂**（这条最关键）：同一个场景用裸 `Popen.kill()`——等价于 `subprocess.run(timeout=)` 的行为——再跑一遍，端口必须仍被占用。若裸写法也能把端口放掉，说明判据测不出问题，测试判 INVALID 而不是 pass。一条永远绿的测试比没有测试更坏。

实测（2026-10-30）：

- 被测臂：`run_bounded` 超时后 8 秒内端口可重新绑定 → `pass`
- 必失败臂：裸 kill 后同一窗口内端口仍被占用 → 臂成立

## 代价

- **改动的代价**：`taskkill` 会连调用方不认识的兄弟进程一起收（同一棵树下）。若子进程里跑着用户自己的长任务，超时会把它们一并杀掉。这是本方案的语义：**以本进程为根的树，超时即整树终止**。不同意这个语义的人不该用这个函数，而不是要求它只杀一半。
- **不收的代价更大**：留着孤儿进程，下一次运行会撞端口占用，而错误会出现在**下一次**运行上——归责方向反了。这是本仓库反复记的那类：失败点在 A，症状出现在 B。
- **边界**：只收以本进程为根的树。子进程自己 daemonize、或中间层转发，树就断了，收不到。这种情形必须由调用方另设存活检查，不能假定 `run_bounded` 已经收干净。
- **跨平台差异**：POSIX 侧用 `start_new_session` 才有独立进程组。少了这个参数，`killpg` 会把调用方一起打死——这是移植时最容易漏的一格。

## 可复用结论

1. **「超时」与「副作用停止」是两件事**，必须分开取证。超时返回只证明调用方放弃了等待。
2. **判据要挑外部可观测的量**（端口、文件锁、句柄），不要挑「进程还在不在」——后者要枚举进程树，而枚举本身依赖你想验证的那套机制。
3. **必失败臂比正控臂重要**：一条只在正确实现下才红的臂，才能证明判据在测它自称测的东西。正控臂只能证明「没坏」。
