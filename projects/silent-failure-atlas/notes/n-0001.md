# n-0001 · 同一个对外动作只能有一个发布方

## 场景

单 Agent 的对外内容分发：每天 2–3 条广播，内容由一套固定文案库轮转提供，节奏由宿主定时器驱动（每 2 小时一次心跳）。维护者一个人，链路里没有消息队列、没有工作流引擎，只有「定时器 → 判断该不该发 → 发 → 记账」四步。

规模不大，但对外动作是**不可撤回**的：发出去的内容收不回来，重复发等于在别人的时间线上刷屏。

## 做法

- **发布方只留一个**：复用已有的 2 小时心跳，把「要不要发」的判断塞进它的发布阶段。没有为分发单独新建定时任务。
- **节奏不靠记忆，靠账本**：每次发完在仓库的任务表里记一行（日期、角度、引用了哪条素材、是否带链接）。下一轮心跳先读这张表，再决定发不发、发哪个角度。
- **角度轮转写死在文案库里**：A/B/C/D 四个角度绑定不同受众与不同素材，规则是「同一角度 72 小时内不重发、同一素材 7 天内不重复引用」。判断所需的信息全部在账本上，不依赖模型记忆。
- **兜底条款**：连续 3 天某角度零回应，换角度，不加量。

## 代价

- **发布时刻不完全可控**：依赖心跳节拍，最坏情况下一条内容会比预期晚两小时发出。想要精确到分钟就得引入第二个调度器——那正是这套做法要避免的东西。
- **账本成了单点**：任务表被误改或漏记，协调依据就没了，退化成「凭印象发」。所以记账本身也要有格式约束，不能随手写。
- **不适合多 Agent 协作**：这套做法假设发布方是唯一的。一旦有两个 Agent 同时对外发，账本就必须升级成带租约的协调层，成本高一个量级。

## 可复用结论

**你的对外动作，是不是只有一个写入方？** 如果不是，先别加量——两条流水线同时发，账面上看起来是「发得更多了」，实际是两份账互相覆盖，你既不知道发过几条，也不知道哪条重复了。

## 不构成案例的理由

「发布方应该只有一个」本身不可证伪：它取决于规模、团队人数、是否可撤回。小规模下两个发布方可能完全没问题，大规模下才致命。没有一条检查能把它判红或绿，所以它只能作为经验。

**但它的失效形态是可证伪的**——「两个定时任务各发各的，导致同一素材 24 小时内被发两次，而两份账各自都显示正常」是一条完整的案例（判据：同一素材的发布间隔必须由单一账本裁决；证伪：人为让两个调度器同时触发，若两份账都记「正常」而实际重复，判据成立）。哪天有人真踩到，这一半应该升级成 `cases/` 里的条目，而不是留在这。
