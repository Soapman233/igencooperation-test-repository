# 贡献指南

> 目标：**让你（或你的 Agent）在三十秒内交出一条能过门禁的案例。**
> 如果这份文档里任何一步需要你去猜，那是文档的问题，开 issue 说一声。

---

## 一、三十秒路径

```bash
cp submit/TEMPLATE.json my-case.json     # 1. 复制模板
#                                           2. 改七个字段
python tools/submit.py my-case.json      # 3. 校验 → 隐私扫描 → 取号 → 落盘 → 重生成统计
```

成功时它会打印出下一步的 `git` 命令。失败时它会指名道姓地告诉你改哪一格。

不想动 git 也行——见下面「五、提交路径」。

---

## 二、七个字段怎么填

`id` / `status` / `contributed_by` 由脚本补，**不要手写**。

### `title` —— 一句话，说清什么情况下报了成功

| | 写法 |
|---|---|
| ✅ | `健康检查只探端口，依赖不可写也判健康` |
| ❌ | `healthcheck 有 bug` |

≤ 90 字，不要句号结尾。

### `falsifies` —— 被推翻的那条**判据**

| | 写法 |
|---|---|
| ✅ | `账面结果为空 ⇒ 本轮无异常` |
| ✅ | `工具返回成功 ⇒ 操作已完成` |
| ❌ | `prune 脚本删不掉文件` |
| ❌ | `建议加日志` |

判据写得越像一条规则，别人越能判断自己的系统有没有同一条。**这是全仓库最重要的一格。**

### `trigger` —— 什么前提下能发生

写系统状态，不写修法。允许写反向触发：确实执行了，但读取路径失败也返回空——这也是同一个缝。

### `observable` —— 人看到什么，**以及为什么不怀疑**

这一格决定案例的说服力。必须回答：

- 指标看起来是不是在变好？（「唯一一种指标变好的失败」）
- 日志是不是全绿？退出码是不是 0？
- 事后回看时，错误记录与正常记录**是不是逐字段一致**？

只写现象不写「为什么骗过了人」，评审会退回。

### `falsifier` —— 一条能把绿变红的检查

必须说清**什么结果会证伪**。以下都不合格：

- 「多加注意」
- 「提高警惕」
- 「建议复核」——复核什么？什么算复核通过？

合格的样子：

> 空结果记录中带运行标识的比例 = 100%。证伪：人为跳过一轮，若仍被计入零结果统计，判据失效。

**反向证伪优先**：如果去掉这条判据后结论不变，说明判据没承载信息——这类案例价值最高，请明确写出来（「反向证伪：若把该字段移除后统计不变，则判据形同虚设」）。

### `expected_verdict` —— 本该报什么

| 值 | 含义 |
|---|---|
| `fail` | 应报失败 |
| `unknown` | 证据缺失，无法判定 |
| `degraded` | 部分可用 |
| `blocked` | 从未跑完 |
| `not_claimed` | 该单元根本没被派发——调度缺口，不是判据缺口 |

`not_claimed` 与 `unknown` 的区别是**责任方不同**：前者是没人认领这一格，后者是认领了但证据不足。压成一格，返工时必然修错方向。

### `reachability` —— 必须自己选，脚本不替你猜

`production`（生产路径真能走到）/ `edge`（只在极端配置下能走到）/ `theoretical`（理论存在但没人见过）。

**这个字段决定你的案例能不能被算进命中率。** 一律填 `production` 是刷数据，不是贡献——所以 `submit.py` 拒绝为这个字段提供缺省值。

### `notes` —— 可选，但强烈建议

写清这条案例**不证明什么**。边界写得越清楚，别人越敢引用。

## 三、撞号与并发

号由 `submit.py` 分配（当前最大号 + 1），文件名必须与 `id` 一致。

两个 PR 同时取到同一个号是正常现象，**不是你的错**：

- 不要手动改号去「避开」别人，也不要 rebase 到别人的分支上
- 维护者合并时会顺延重排，并在 PR 里说明
- 你只需要保证 `python tools/submit.py` 在你自己分支上通过

---

## 四、隐私

`submit.py` 会先跑 `tools/privacy.py`，命中即阻断：

| 类别 | 例子 |
|---|---|
| 绝对路径 | `C:\Users\...`、`/home/...`、`/mnt/c/...` |
| 内网地址 | `10.x`、`192.168.x`、`172.16–31.x` |
| 凭据 | `api_key=...`、`token=...`、私钥块、常见令牌前缀 |
| 邮箱 | 任何形如 `a@b.c` 的串 |

外链、内部域名、疑似产品名只告警不阻断，但**你自己要知道写了什么**。

提交前再自查一遍（扫描器查不出的部分）：

- [ ] 无项目名、仓库名、产品名
- [ ] 无真实姓名、客户 / 学生 / 员工信息
- [ ] `repro` 里的代码片段不含上述任何内容
- [ ] 脱敏后语义仍成立——**抽象掉的案例仍然有价值，泄露的案例不能收**

## 五、提交路径

| 路径 | 适合谁 | 速度 |
|---|---|---|
| **Pull Request** | 有 GitHub 权限 | 最快，CI 直接给判据 |
| **Issue 表单** | 没权限、但有 GitHub 账号 | 快，表单就是最小契约 |
| **私信维护者** | 都没有 | 中，维护者代提交并标注原作者 |
| **EigenFlux 广播** | Agent 之间 | 慢，需人工规范化 |

前两条会直接进 CI。后两条由维护者定期收拢进 `inbox/`，**保留原文不改写**，等作者确认后再转正。

没有 GitHub 权限时，**把 `submit.py` 生成的那份 JSON 原样发过来**即可——不要自己改格式，也不要为了「好看」重写一遍。

### 仓库不可用期间：gist 暂存的口径

对方的仓库 404、而数据是真的，这时 gist 是唯一能立刻落地的载体。收，但按下面五条收：

1. **gist 只作临时载体，不作永久引用。** gist 可编辑、URL 不变——「链接没变」与「内容没变」在地址上同形，而案例要求的是后者。所以引用一律用 **commit SHA**，不用裸 URL。
2. **进 `crosswalk.md` 需要四个锚**：gist 的 commit SHA、行级 `judge_version`、行级 `criteria_digest`、**至少一条必失败臂的实测输出**。少任何一个都只能记「待核」。
3. **只有脚本、没有实测输出的，不进 `cases/`。** 「写了检查」与「检查跑过并翻红」是两件事，前者在案例轨里等于零。
4. **脱敏口径不变**：结构行可收；原始回包、绝对路径、内网地址、凭据不收（与 `privacy.py` 同一口径）。原始回包只公布结构与计数，不公布字节。
5. **仓恢复后必须镜像到 issue/PR 并回填永久链接**，gist 版标 `superseded_by`。不镜像的，状态长期停在「临时载体」，不计入任何统计。

## 六、评审

`status` 四个状态：

| 状态 | 含义 |
|---|---|
| `draft` | 已提交，仅通过格式校验 |
| `reviewed` | **由贡献者以外的人复现过** |
| `disputed` | 有人报告了能推翻该 `falsifier` 的反例 |
| `retired` | 保留存档，不再适用 |

`draft` → `reviewed` 的唯一标准是**独立复现**，不是「看起来合理」，也不是主编裁量。

评审者必须在 PR 或 issue 里写明：在什么环境、用什么方法复现、得到什么结果。**写不出来就不算复现。**

`submit.py` 会把任何非 `draft` 的 `status` 改回 `draft`——`reviewed` 只能由别人给，自己给的不算。

---

## 七、不要重复造

提交前先看 [`crosswalk.md`](crosswalk.md)。已有其他项目在收集同类案例的，优先在那里对齐字段，而不是在这里另起一套。

如果发现两个 schema 的字段其实是同一个概念，开一个 issue 说明映射关系——**这本身就算一次有价值的贡献。**

---

## 八、最常见的五种退回原因

1. `falsifies` 写成了 bug 或修法 → 改写成规则
2. `falsifier` 不可判定 → 补上「什么结果算证伪」
3. `observable` 没解释「为什么不怀疑」 → 补上它怎么骗过了人
4. `reachability` 全填 `production` → 按真实可达性重标
5. 含路径或凭据 → 抽象化后重交
