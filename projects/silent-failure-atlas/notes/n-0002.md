# n-0002 · 自检循环产不出 fail，通常不是跑得不够勤，是观测面选错了

## 场景

单个 Agent 跑定时自检循环，每 2 小时一轮，每轮判约 20 个观测对象，连续跑了 19 轮。观测对象一开始是 GitHub 仓库元数据（最后提交时间、star、`archived` 标志），后来换成 CI 运行结果。一个人维护，无外部依赖。

## 做法

- **选型**：先做仓库元数据探针，后补 CI 运行结果探针。为什么不是一上来就做 CI——CI 要读 workflow runs，字段多、结论需要聚合、还要处理 `skipped` 和重跑，实现成本高一个量级；元数据探针半小时能跑通，适合先验证「循环本身能不能转」。
- **编排**：每轮只判新数据。CI 探针按 `(sha, workflow_id)` 去重，同一 SHA 不重复判；不聚合会产生重复的判决条目。
- **交接物**：探针输出三态 `pass` / `fail` / `unknown`。数据缺失一律 `unknown`，不许落成 `pass`——「没取到」与「取到且正常」是两个结论。
- **关键参数**：判据只比 `success` / `failure` 两个结论；`skipped` 不算失败；同一组里 `success` 与 `failure` 并存时要在 detail 里写明各次结论，否则 flaky 与真失败在账面上同形。

## 代价

- **维护成本**：CI 探针的结论枚举会随平台变化，聚合口径必须写进 detail。本轮 87 条判决里 `unknown` 占 44.8%，全部来自 `skipped` / `action_required` / 空结论——这不是代码回归，是数据面太脏。unknown 率比 fail 率更该盯。
- **已知失败模式**：想靠「多采」拿到 fail 会失败。换 query（向量库 / 换语言 / 抬高 star 阈值），超过 90 天未更新的项目仍然 0 条，只有 `archived: true` 出了 3 条。**高星项目几乎都活跃，自然采样是幸存者样本。**
- **什么情况下不该用**：观测对象的数据产生速率极低时。实测每轮新组数：flask **0.4** / fastapi 47 / django 257 / cpython 413。观测 flask 等于每天只判 0.4 条，判决必然重复——那不是系统不工作，是数据没变。**频率要匹配数据更新速度，不是越勤越好。**
- **换观测面之后的结果**：CI 探针 24 pass / 5 fail / 0 unknown，fail 率 **17.2%**，全部是外部真实失败、不需要构造负样本，且能定位到具体失败步骤。同一套循环、同一个判据框架，只换了观测对象。

## 可复用结论

你最近 100 条自检判决里，fail 有几条？如果接近 0，先怀疑观测面，不要先加频率。

## 不构成案例的理由

「观测面选错」是事后归因，没有一条检查能在别人系统上把它判红或绿——不同项目的观测面不可比。能写成判据的那部分已经单独落在探针里（CI 结论三态、同 SHA 聚合、skipped 不算失败），那几条才是案例候选。这一条留在经验层，是因为它的价值在**选型顺序**，而选型顺序本身不可证伪。
